# EPIC-4-QR-003 - Public QR Verification API

## Objective

Implement the unauthenticated, read-only verification endpoint that validates an approved QR and returns only the approved non-sensitive traceability summary.

## Scope

Implement `GET /api/v1/verify/{qrId}` using QR-001's identifier and response contract: locate the QRRecord, recover the canonical payload, recompute HMAC-SHA256, determine valid/invalid status, resolve the linked Lot and permitted origin summary, and return structured outcomes.

## Out of scope

Authenticated full trace retrieval, QR generation, UI, event mutation, PII exposure, exact polygon coordinates, GIN-format decisions, public write operations, rate limiting/infrastructure not specified, and enterprise security mechanisms.

## Preconditions and dependencies

QR-001 approved; QR-002 merged with test data and an actual persisted signed QRRecord; EPIC-3 trace chain verified. Dependency: QR-002 for the stored representation and identifier contract. If public fields or invalid-record semantics remain unspecified, stop and record **Traceability gap - requires review.**

## Inputs and expected outputs

Input: public `qrId` path value or approved verification URL token. Output: exact QR-001 response for valid, tampered, malformed, unknown, inactive, or deleted QR cases. Valid output contains only approved summary fields such as GIN/coarse origin if explicitly approved; invalid output must not disclose internal details.

## Relevant files/modules

`backend/app/api/v1/` verify router, `backend/app/schemas/` public verification schema, `backend/app/services/` verification service, QRRecord/CoffeeLot/Farm query modules, `backend/tests/`, and Postman collection location established by the repository.

## Backend responsibilities

Validate the public identifier, recompute the signature from the exact canonical payload, retrieve the linked Lot/origin safely, minimize the response, and return predictable errors without stack traces.

## Frontend responsibilities

None beyond the response contract consumed by QR-005.

## Database responsibilities

Read QRRecord and linked Lot/Farm data using ORM/parameterized access. Do not mutate records. Handle missing/inactive/deleted records as QR-001 specifies.

## API requirements

`GET /api/v1/verify/{qrId}` is intentionally unauthenticated, read-only, versioned, and public. It must distinguish valid/invalid according to the approved contract while avoiding identifier enumeration detail beyond the approved response.

## Security requirements

Treat the payload and identifier as hostile input. Reject tampering, malformed encoding, unknown identifiers, nonexistent Lots, and inactive/deleted records. Never expose HMAC key, farmer national ID, phone, exact coordinates, SQL errors, or internal stack traces. Confirm public endpoint is the only unauthenticated feature introduced by this epic.

## Acceptance criteria

- A QR generated by QR-002 returns the approved valid result and permitted origin summary.
- Tampered payload/signature is rejected as invalid without sensitive detail.
- Malformed, unknown, nonexistent, inactive, or deleted records receive the approved structured outcome.
- No authentication is required for this read-only endpoint, while no public write or full protected trace data is exposed.
- Response fields exactly match QR-001 and contain no unapproved PII or secret material.

## Testing requirements

Unit tests for HMAC recomputation and malformed input; API tests for valid, tampered, unknown/nonexistent, inactive/deleted, and public-data minimization cases; Postman request; unauthenticated access check; regression suite; manual browser/API check with synthetic data.
